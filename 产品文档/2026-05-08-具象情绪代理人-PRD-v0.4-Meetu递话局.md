## 0. 先纠偏：编辑部不是我们的最终答案

上一版“情绪编辑部”解决了统一性，但它仍然有问题：

1. **它是别人的成功逻辑的迁移**：排版小动物像编辑部，是因为它本身就是文案/排版/创作语境；
2. **它更偏内容生产，不够 Meetu**：编辑部是在“写稿”，但 Meetu 的核心应该是“人与人之间如何低压连接”；
3. **它还是站在内容工具侧**：用户像是在找人帮自己写一段话，而不是把自己的状态递给别人；
4. **它对社交闭环解释不够自然**：朋友的回复像读者评论，不像真实关系里的“接话”。

所以这次重构不吃“编辑部”的老本。

我们要找的是更适合 Meetu 的母框架。

## 1. 重新过一遍所有关键约束

### 1.1 第一性原理

这个应用必须同时具备：

| 原则 | 产品含义 |
|---|---|
| 传播性 | 用户愿意发出去，别人看到有话接 |
| 复用性 | 不是一次性测试，而是每天/每个状态都能用 |
| 情感情绪依赖性 | 用户会依赖某个具象对象替自己表达 |
| 爆款潜质 | 有命名、截图、接龙、二创、朋友互贴标签能力 |

### 1.2 排版小动物给我们的真实启发

排版小动物不是因为“动物”成功，也不是因为“编辑部”成功。

它真正击中的点是：

> 用户本来就有表达/分享需求，但自己懒得写、不好意思写、写不好。小动物作为一个被喜欢的具象个体，替用户完成表达。

所以我们要学的是：

- 内源需求：用户本来就想表达；
- 低门槛：不用想复杂输入；
- 具象承接：有一个可喜欢的对象替我说；
- 可转发：结果本身就是社交材料；
- 可复用：不是一次性内容，而是持续嘴替。

不是学：

- 一定要小动物；
- 一定要编辑部；
- 一定要排版模板；
- 一定要做测试。

### 1.3 DavidC 的关键点

DavidC 提过的点必须保留：

1. 朋友锐评应该发生在分享后的评论区/群聊，而不是写死在图上；
2. 不同场景、语气、对话风格可以人格化；
3. 降低 friction 不能一刀切，要和搜集足够信息平衡；
4. 技术 MVP 不应过复杂。

### 1.4 Jonathan 的关键点

Jonathan 提过的点也必须保留：

1. 不能把“朋友”抽象成一个空概念，要有具象、被喜欢、可寄托的对象；
2. 不限小动物，角色形态可以重新定义；
3. 角色不能割裂，必须是一个整体设计；
4. 链路不能长，不能靠用户回复/填表/组织到场；
5. 必须切内源需求，不是运营强推；
6. 产品要有爆款潜质，不是漂亮但没人用的功能。

## 2. 我们自己适合什么框架？

Meetu 的底层不是“写稿”，而是：

> 帮用户更低压地和别人产生连接。

所以我们自己的框架应该围绕“把话递出去”，而不是“把稿写好”。

我建议新母框架：

# Meetu 递话局

一句话定义：

> 一个替用户把说不出口的状态，包装成一张可以发出去、让别人自然接话的“递话卡”的小应用。

用户感知：

```text
有些话自己说太认真。
交给递话局递一下。
```

更短：

```text
今天不想解释。
找个小东西替我递话。
```

## 3. 为什么是“递话局”，不是“编辑部”

| 维度 | 编辑部 | 递话局 |
|---|---|---|
| 核心动作 | 写稿/改稿 | 把话递给别人 |
| 更像谁 | 内容生产工具 | 社交连接工具 |
| 与 Meetu 的关系 | 弱，偏内容 | 强，偏遇见/连接 |
| 分享后发生什么 | 读者评论 | 朋友接话/回话 |
| 用户心理 | 帮我写得好一点 | 帮我把不好意思说的话递出去 |
| 复用路径 | 每天写稿 | 每天递不同状态 |
| 情感寄托 | 编辑懂我 | 小信使替我出面 |

“递话局”更贴近 Meetu：不是生产内容，而是降低人与人之间开口和接话的压力。

## 4. 产品世界观

### 4.1 世界观一句话

> Meetu 递话局里有一群不太正经的小信使，专门替你把今天说不出口的话，递成一张能发出去的状态卡。

### 4.2 用户是谁

用户不是被测试者，不是写稿人，也不是模板填写者。

用户是：

> 有话想递出去，但不想自己说得太明显的人。

### 4.3 代理人是谁

代理人不是“朋友”，也不是“评价者”。

代理人是：

> 替你递话的小信使 / 递话员 / 状态投递员。

它负责把你的状态变成一张不那么尴尬、朋友能接住的卡。

### 4.4 朋友是什么角色

朋友不是产品里的抽象角色。

朋友只在分享后出现：

- 群聊里回“这不就是你”；
- 评论区补一句；
- 给你改备注；
- 让你也给 ta 递一张。

这保留真实社交关系的活性。

---

## 5. 核心心理机制

### 5.1 可否认性

用户可以说：

```text
我只是发了张卡。
不是我在认真表达。
```

代理人替用户承担“表达太直白”的风险。

### 5.2 第三方缓冲

原本用户要说：

```text
我今天不想社交。
```

现在变成：

```text
低电量信使替我递话：
人在，电不在。
```

情绪被一个具象对象缓冲后，更容易发出去。

### 5.3 被接住的期待

用户不是为了广播，而是为了等别人接话。

一张好卡应该让朋友能回：

- “懂了”；
- “这不就是你”；
- “我也要一张”；
- “今天你确实这个状态”。

### 5.4 角色依赖

用户不是依赖功能，而是依赖某个“替我递话的小东西”。

比如：

- “我今天又要找低电量信使”；
- “嘴硬信使太懂我”；
- “这个状态适合让边界信使去递”。

## 6. 产品结构

### 6.1 P0 主流程

```text
入口：今天有什么话不好自己说？
  ↓
选择递话员
  ↓
选择今天要递的状态
  ↓
选择递到哪里（可跳过）
  ↓
生成 3 张递话卡
  ↓
保存 / 换一张 / 给朋友也递一张
  ↓
用户发出去
  ↓
朋友接话
```

### 6.2 输入控制

P0 不让用户写长文本，也不做自由 AI。

只问三件事：

1. **让谁递？** 具象代理人选择；
2. **递什么状态？** 今日状态选择；
3. **递到哪里？** 群聊 / 朋友圈 / 微信状态，可跳过。

这比“目的、偏好、边界”轻，但比一键随机更能贴脸。

### 6.3 输出

输出不是“结果卡”，而是“递话卡”。

卡上写：

- 谁替你递；
- 它递了什么话；
- 现在是什么状态；
- 留一个朋友接话口。

## 7. 角色系统：同属“递话局”

角色不能再割裂。

所有角色都属于 Meetu 递话局。它们不是动物集合，也不是系统拼盘，而是不同职能的递话员。

### 7.1 P0 递话员

| 递话员 | 负责状态 | 性格 | 典型话术 |
|---|---|---|---|
| 低电量信使 | 社交耗电、拒绝营业 | 软塌塌但诚实 | 人在，电不在 |
| 嘴硬信使 | 被说中但不认 | 表面倔，实际全暴露 | 我没有，只是有点像 |
| 后台信使 | 脑内过载、复盘 | 表面正常，后台爆炸 | 前台已回复，后台还在开会 |
| 边界信使 | 勿扰、边界、私人空间 | 礼貌但会关门 | 今日不对外开放 |
| 出门信使 | 想去但懒、临时局 | 已经出发，精神上 | 申请已提交，床不同意 |
| DDL 信使 | 期末、拖延、崩溃 | 假装稳住，实际很慌 | 还有时间，理论上 |

### 7.2 为什么这组比 v0.3 更适合

v0.3 “编辑”统一但偏内容机构。  
v0.4 “信使/递话员”统一且偏社交连接。

它更符合 Meetu：

- Meetu 不是帮人写稿，而是帮人开启关系里的轻互动；
- 递话天然连接“我”和“别人”；
- 朋友的回复就是“回信/回话”，链路自然；
- 角色有情感寄托，但不抢真实朋友的位置。

### 7.3 角色形象要求

角色可以是动物、物件、小怪物、小人，但必须统一为“递话局员工”。

统一视觉元素：

- 小包/信封/便签/邮戳/回执；
- 小窗口/投递箱/传话筒；
- 状态贴纸；
- 已送达/待回复/本人暂不解释；
- 同一材质、线条、排版语言。

禁止：

- 一个像动物园；
- 一个像系统弹窗；
- 一个像办公室；
- 一个像神明；
- 互相没有关系。

## 8. 状态系统

### 8.1 P0 状态池

| 状态 | 适配递话员 |
|---|---|
| 低电量 | 低电量信使 |
| 在线装死 | 低电量信使 / 嘴硬信使 |
| 被说中了但不认 | 嘴硬信使 |
| 脑内过载 | 后台信使 |
| 社交售后复盘 | 后台信使 |
| 今日勿扰 | 边界信使 |
| 想去但懒 | 出门信使 |
| 出门启动失败 | 出门信使 |
| DDL 在追 | DDL 信使 |
| 假装来得及 | DDL 信使 |
| 需要朋友捞一下 | 低电量信使 / 边界信使 |
| 表面正常 | 后台信使 / 嘴硬信使 |

### 8.2 状态选择文案

不要写得像心理测评。

错误：

```text
请选择你当前的社交心理状态。
```

正确：

```text
今天这句话大概是什么状态？
```

或：

```text
这封话想递成什么味儿？
```

## 9. 输出卡结构

### 9.1 基础结构

```text
Meetu 递话局

低电量信使 · 已送达

人在。
电不在。

状态：低电量社交中

收到请不要催更。
```

### 9.2 关键设计

| 元素 | 作用 |
|---|---|
| Meetu 递话局 | 产品整体记忆 |
| 递话员 | 角色依赖 |
| 已送达/待回复 | 社交连接感 |
| 主句 | 替用户表达 |
| 状态标签 | 朋友认领锚点 |
| 接话口 | 引导朋友回复 |

### 9.3 卡片不要写什么

不要写：

- “朋友锐评”；
- “你是 XX 型人格”；
- “精准分析”；
- “分享给朋友”；
- “下载 App”；
- 太完整的解释。

卡片必须像用户自己愿意发的状态，不像产品广告。

## 11. 传播机制

### 11.1 图是“递话”，不是“结果”

用户分享时不需要说：

> 我测出来是什么。

而是：

> 这张替我说了。

这比测试更高频，因为每天都有状态可以递。

### 11.2 朋友评论是“回话”

分享后的互动可以被设计成：

- 已签收；
- 已读；
- 回信；
- 补充说明；
- 代收人：某某朋友。

但这些不要强做功能，先作为文案和视觉语言。

### 11.3 二次传播

天然二次传播路径：

```text
用户发递话卡
  ↓
朋友评论“这不就是你”
  ↓
用户截图评论
  ↓
朋友问在哪递
  ↓
用户把链接发给朋友
  ↓
朋友给自己/别人递一张
```

## 12. 复用机制

### 12.1 每日递话

每天都可以递一句不同状态。

不是每天“测我是谁”，而是每天“替我说今天”。

### 12.2 常用信使

用户会形成默认信使：

- “我常驻低电量信使”；
- “嘴硬信使今天又替我嘴硬了”；
- “DDL 信使最近夜班很多”。

### 12.3 递话箱

P0 可做本地历史：

- 最近递过；
- 常用信使；
- 收藏句子；
- 给朋友递过。

名字可以叫：

```text
我的递话箱
```

这比“卡册”更符合世界观。

### 12.4 给朋友递一张

扩散按钮：

```text
给朋友递一张
```

而不是：

```text
分享给朋友
```

前者有世界观，后者像工具按钮。

---

## 13. 为什么这个方向更适合 Meetu

### 13.1 Meetu 的底层是连接

Meetu 不应该只做内容生成。

Meetu 要解决的是：

> 用户想和别人发生低压连接，但不知道怎么开口、怎么表达、怎么让别人接住。

“递话局”正好承接这个动作。

### 13.2 递话比编辑更社交

编辑部的结果是稿子。  
递话局的结果是关系里的回话。

我们要的不是“内容完成”，而是“互动开始”。

### 13.3 递话可以向 Meetu 主产品延展

未来可以自然连接：

- 给朋友递一张；
- 给群里递一张；
- 给某个活动递一句开场；
- 给搭子局递一个低压自我介绍；
- 给陌生人递一个不尴尬的状态信号。

这比“编辑部”更能回到 Meetu 的长期产品方向。

## 14. MVP 范围

### 14.1 P0 做什么

- 6 个递话员；
- 12 个状态；
- 每个状态 4-6 条递话文案；
- 3 个投递场景：群聊 / 朋友圈 / 微信状态；
- 每次生成 3 张递话卡；
- 保存图片；
- 换一句；
- 给朋友递一张；
- 我的递话箱（本地历史）；
- 基础埋点。

### 14.2 P0 不做什么

- 不做 AI 自由生成；
- 不做账号系统；
- 不做公开广场；
- 不做匿名评价；
- 不做复杂编辑器；
- 不做匹配；
- 不做“朋友锐评生成器”。

### 14.3 技术复杂度

P0 仍是轻 H5：

- 静态文案池；
- 规则映射；
- html2canvas/canvas 导图；
- localStorage；
- 简单埋点。

不需要后端即可验证。

## 15. 视觉系统

### 15.1 母视觉：递话局

关键词：

- 信封；
- 便签；
- 小邮戳；
- 派送单；
- 已送达章；
- 递话箱；
- 小窗口；
- 代收/签收/待回复；
- 纸感但不复古；
- 轻松但不幼稚。

### 15.2 角色视觉

所有角色统一在“递话局”系统中。

每个递话员可以有不同人格，但必须共享：

- 同一线条系统；
- 同一纸张/贴纸/邮戳语言；
- 同一状态标签；
- 同一品牌露出方式；
- 同一截图传播比例。

### 15.3 不要做成什么

- 不要做成邮政复古风太重；
- 不要做成儿童可爱邮差；
- 不要做成品牌官方通知；
- 不要做成外卖/快递广告；
- 不要做成六个无关 IP。

它应该像：

> 一个大学生自己会愿意截图转发的“不正经状态投递系统”。

## 16. 内容原则

### 16.1 短

递话不应该长。

核心句最好 8-18 字。

### 16.2 不解释

不要解释心理原因，只递一句能被接住的话。

错误：

```text
你因为长期社交消耗过高，所以需要独处恢复。
```

正确：

```text
人在，电不在。
```

### 16.3 有回话口

每张卡都要让朋友能回。

例如：

```text
收到请不要临时安排我。
```

比：

```text
我今天很累。
```

更容易接话。

### 16.4 不冒犯

嘴损可以，但不能让用户觉得被审判。

产品不是说：

```text
你就是这样的人。
```

而是说：

```text
今天先让它替你这么说。
```

## 17. 验证计划

### 17.1 先做 6 递话员压力测试

每个递话员出：

- 1 个名字；
- 1 个视觉小样；
- 10 条递话文案；
- 3 张卡片 demo。

内部评估：

- 是否愿意发？
- 是否想发给某个朋友？
- 朋友是否能接话？
- 是否能连续使用 7 天？
- 是否有外号/二创潜质？

### 17.2 再做 H5 MVP

如果 6 个递话员里至少 3 个明显成立，再做 H5。

不要先重工程。

### 17.3 渠道测试

- 微信群：看朋友是否接话；
- 小红书：看是否有人问入口；
- 朋友圈/微信状态：看是否愿意展示；
- 内部大学生样本：看是否愿意连续用。

## 18. 当前 PM 判断

我现在收回“编辑部是最终框架”的判断。

更适合 Meetu 的母框架应该是：

# 递话局 / 状态投递系统

原因：

1. 它更贴近 Meetu 的连接本质；
2. 它不是借别人的编辑部逻辑；
3. 它能统一角色、视觉、文案、分享后的评论关系；
4. 它天然解释“朋友锐评发生在分享后”；
5. 它有更强的情绪依赖和复用空间；
6. 它可以从状态卡延展到未来的搭子、活动、低压自我介绍。

如果要继续推进，我建议下一步不是再写 PRD，而是做：

> 6 个递话员 × 每个 10 条文案 × 每个 3 张卡片 demo

用真实 demo 判断这个世界观是否有爆款潜质。
