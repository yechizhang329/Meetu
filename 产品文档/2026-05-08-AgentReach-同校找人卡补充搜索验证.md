## 2. 先给结论

**方向支持，但需要收窄。**

上一版我叫它“同校找找卡 / 校园需求卡”，这个说法太 PM。经过补验证后，应收窄为：

# 校园找人卡生成器

一句话：

> 把“我想找个____”变成一张不尴尬、边界清楚、能发群/发帖/发朋友圈的卡。

P0 不要做泛“需求卡”，先做 3 个用户已经听得懂的模板：

1. `找搭子卡`
2. `自介 / 扩列条`
3. `求助 / 求资源卡`

P1 再做 `组局 / 约伴卡`。

## 3. 严格过滤后的核心数据

为避免把“泛文案/泛排版”误判成产品需求，我按更严格关键词过滤了一遍：

| 核心信号 | 命中笔记 | 总互动分* | 评论量 | 评论占比 | 说明 |
|---|---:|---:|---:|---:|---|
| 搭子/找搭子/饭搭子/学习搭子/聊天搭子 | 192 | 423,579 | 132,001 | 31.2% | 行动意图最强，评论区直接在找人 |
| 扩列/交友/自介条 | 92 | 312,238 | 92,329 | 29.6% | 已有“自我表达模板”行为 |
| 求助/互助群/求资源 | 26 | 160,708 | 27,912 | 17.4% | 有评论承接，但范围更杂 |
| 明确卡片/模板/文案需求 | 17 | 69,652 | 5,674 | 8.1% | 证明用户会找可复制/可截图表达载体 |
| 明确边界字段（女生/同校/不日抛/1v1/城市/wx 等） | 162 | 791,940 | 168,761 | 21.3% | 证明“边界条件”不是 PM 想象 |

\*互动分 = 点赞 + 2×评论 + 收藏 + 分享，用来放大“评论即行动”的信号。

关键解读：

- `搭子/扩列` 的评论占比分别达到 31.2% / 29.6%，明显是“我也要 / 我也来 / 能不能加我”的行动型需求，不是纯内容消费。
- `明确卡片/模板/文案需求` 只有 17 条，但它证明“生成图片/模板”是可行实现方式；真正的需求本体不是图片，而是低尴尬表达。
- `边界字段` 命中 162 条，说明用户不是只说“找朋友”，而是会自然带上性别、城市、关系强度、是否长期、场景等条件。

## 6. 验证点 C：边界字段必须做，不然回复质量会差

样本里自然出现的边界词包括：

- 人群：女生、男生、女研、大学生、应届生
- 地域：同校、同城、上海、武汉、北京
- 关系强度：1v1、长期、不日抛、固聊
- 场景：学习、聊天、王者、旅游、饭搭子
- 私域动作：wx、微信、私、加

代表样本：

| 样本 | 评论 | 暴露的边界字段 |
|---|---:|---|
| `上海应届生找搭子` | 3,262 | 城市 + 身份 |
| `找1v1聊天搭子` | 3,975 | 关系形式 + 场景 |
| `王者搭子dd（女生想找女生）` | 2,753 | 游戏场景 + 性别边界 |
| `固聊` | 4,696 | 长期聊天关系 |
| `找搭子，可加wx，一起努力吧` | 3,227 | 学习/努力场景 + 私域承接 |

结论：P0 表单不能只有“标题 + 文案”。最小字段应该是：

1. 我想找什么
2. 场景
3. 学校/城市（可公开/可模糊）
4. 边界条件
5. 回复暗号

## 8. 命名修正：不要叫“需求卡”

用户自然语汇是：

- 找搭子
- 蹲搭子
- 搭子 dd
- 扩列
- 自介条
- 交友卡 / 交友帖
- 求助帖
- 互助群
- 约伴 / 组局

所以：

- 内部项目名可以叫 `校园需求卡`。
- 用户侧不要叫 `需求卡`，更不要叫 `需求匹配系统`。
- 用户侧建议叫：`找搭子卡`、`自介条`、`求助卡`、`组局卡`。
- 统一外壳文案：**把你想找的人/事，做成一张能发出去的卡。**

## 9. 推荐 P0 形态

一个 H5，30 秒生成一张卡。

### 输入

| 字段 | 示例 | 必要性 |
|---|---|---|
| 卡型 | 找搭子 / 自介扩列 / 求助 / 组局 | 必填 |
| 场景 | 自习、聊天、王者、饭搭子、资料、互助群 | 必填 |
| 学校/城市 | 同校、武汉、上海、可不公开 | 选填 |
| 边界 | 只女生、不日抛、1v1、不露脸、预算、时间 | 必填/可多选 |
| 回复暗号 | 评论区打 dd / 回“自习” / 私我“群” | 必填 |

### 输出

1. 图片卡：适合发小红书群、朋友圈、学校群。
2. 复制文案：适合直接发帖/评论/群聊。
3. 匿名数据：卡型、场景、学校/城市、边界、保存/复制事件。

## 10. P0 卡型优先级

| 优先级 | 卡型 | 为什么先做 |
|---|---|---|
| P0-1 | 找搭子卡 | 数据里行动意图最强，评论区直接在找人 |
| P0-2 | 自介 / 扩列条 | 已有成熟语汇和图片化表达习惯，传播成本低 |
| P0-3 | 求助 / 求资源卡 | 能承接校园信息差，但先做具体求助，不做资料站 |
| P1 | 组局 / 约伴卡 | 场景丰富，但线下安全和履约边界更复杂 |

## 11. 还要验证的点

1. **卡片视觉哪种更容易被转发**：证件卡、自介条、便签卡、招领/公告式，至少做 3 张 A/B。
2. **用户是否愿意写学校**：公开帖有人写城市/身份，但真实 H5 里可能担心隐私；需要“同城/同校/不公开学校”三档。
3. **小红书群是否适合发卡**：公开帖导流风险高，群内可用图 + 暗号，但需要单独测群内文本风险。
4. **能否沉淀到 Meetu**：如果只生成图，流量可能跑掉；必须记录匿名需求数据和保存/复制行为。

## 12. PM 判断

这轮补验证后，我不建议继续泛泛讨论“还能做什么类似排版小动物的东西”。更准确的产品机会是：

> **大学生有大量临时小需求，不知道怎么低尴尬地发出去。我们先做一个校园找人卡生成器，把这些需求包装成可传播、可回应、可沉淀的卡。**

为什么它是当前低成本 / 高潜在收益比值最好的方向：

- 成本低：H5 表单 + 模板渲染 + 保存图 + 复制文本，不需要先做登录/匹配/供给库。
- 收益高：切中评论区已存在的行动需求，尤其是搭子/扩列/求助。
- 和 Meetu 相关：它天然连接同校找人、校园互助、活动组局和后续交易闭环。
- 风险可控：用户自己决定公开什么，产品只帮他表达清楚，不直接撮合敏感关系。

下一步如果 Jonathan 认可这个方向，我建议进入 PRD 前先问 6 个具体问题：卡型优先级、学校字段是否必填、是否允许匿名、是否需要登录、是否保存需求墙、是否先做小红书群投放版。
