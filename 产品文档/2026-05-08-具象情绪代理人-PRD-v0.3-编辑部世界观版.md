## 0. 本次关键修正

Jonathan 指出：

> 角色选取撕裂。排版小动物是一个编辑部，整个应用也应该是一个具备整体性的设计。现在所有的都是割裂的。

这个判断是对的。

v0.2 的问题是：角色虽然都能“替用户说话”，但来源散乱：动物、系统、物件、部门、神明混在一起，缺少一个统一的母世界观。这样会导致：

- 用户记不住产品整体，只记住零散梗；
- 设计无法形成统一语言；
- 角色之间没有组织关系，难以持续扩展；
- 产品不像一个可依赖的系统，更像一堆模板；
- 很难形成爆款 IP，因为没有共同身份。

所以 v0.3 必须先解决：

> 这些角色到底来自哪里？他们为什么都在这里？他们共同为用户做什么？

---

## 1. 新核心定义：不是“角色集合”，而是“情绪编辑部”

产品应被定义为：

> 一个替用户编辑、翻译、包装当日状态的 **情绪编辑部**。

用户不是在随机选一个角色，而是在找一个编辑部成员帮自己发一条状态。

用户感知：

```text
今天不知道怎么说。
交给编辑部处理一下。
```

或者：

```text
今天的我，需要被编辑一下。
```

这比“小动物/系统/物件大杂烩”更完整。

---

## 2. 第一性原理如何落到“编辑部”

### 2.1 传播性

编辑部天然能产出“可发布内容”。

用户发出去时不是：

> 我生成了一张图。

而是：

> 编辑部给我写了一条今天的状态。

这更像内容产品，而不是工具产品。

### 2.2 复用性

编辑部可以每天工作。

今天处理低电量，明天处理嘴硬，后天处理 DDL，角色和栏目都能长期复用。

### 2.3 情绪依赖性

用户会逐渐形成：

- “今天找哪个编辑？”
- “这事适合交给谁写？”
- “我常驻哪个栏目？”
- “编辑部今天又懂我了。”

这比“选一张模板”更容易形成依赖。

### 2.4 爆款潜质

编辑部世界观能支持：

- 栏目化；
- 角色 IP；
- 投稿感；
- 用户报栏目/报编辑；
- 评论区补稿；
- 系列化运营；
- 未来扩展新编辑、新栏目、新特刊。

## 3. 产品世界观

### 3.1 世界观一句话

> 有一个不太正经但很懂你的编辑部，专门把你说不出口的状态，改成一张可以发出去的图。

### 3.2 用户和编辑部的关系

用户不是“被测试的人”，也不是“模板填写者”。

用户是：

> 今日状态的投稿人。

编辑部是：

> 替用户把状态改成能发出去的内容的人。

流程：

```text
用户投递今日状态
  ↓
编辑部接稿
  ↓
某个编辑负责改稿
  ↓
生成一张可发布状态卡
  ↓
朋友在评论区/群聊补充“读者来信”
```

### 3.3 产品人格

编辑部不是官方、不是心理咨询、不是客服。

它的气质应该是：

- 懂梗；
- 嘴损但不冒犯；
- 不讲大道理；
- 像同龄人帮你润色；
- 会把尴尬状态变得好发；
- 有一点混乱但很会写标题。

## 4. 核心命名方向

### 4.1 产品命名候选

| 名称 | 说明 |
|---|---|
| 情绪编辑部 | 最直观，清楚说明产品机制 |
| 今日状态编辑部 | 更贴近日更和高频使用 |
| 发疯编辑部 | 更传播，但覆盖面窄 |
| 嘴替编辑部 | 强功能，但略像文案工具 |
| 我的状态编辑部 | 更个人化，适合 H5 |
| 不正经编辑部 | 有调性，但功能不够直观 |

我建议 P0 暂用内部名：**情绪编辑部**。  
对外可测试：**今日状态编辑部** / **发疯编辑部** 两个版本。

### 4.2 用户入口文案

```text
今天的你，交给哪个编辑处理？
```

或：

```text
把今天的状态投给编辑部。
```

或：

```text
今天不想自己解释，交给编辑部写。
```

## 5. 角色系统：编辑部成员，而不是随机角色

角色要全部统一为“编辑部成员”。

每个角色都有固定岗位、固定栏目、固定写法。

### 5.1 P0 编辑部成员

| 编辑 | 岗位 | 负责情绪 | 写稿风格 |
|---|---|---|---|
| 省电编辑 | 值班编辑 | 低电量、拒绝营业、在线装死 | 短句、少解释、低声量 |
| 嘴硬编辑 | 标题编辑 | 被说中但不认、嘴硬、自我辩护 | 先否认，再暴露 |
| 后台编辑 | 内心戏编辑 | 脑补、复盘、聊天过载 | 表面/后台双层结构 |
| 边界编辑 | 校对编辑 | 勿扰、边界、需要空间 | 克制、礼貌、明确边界 |
| 出门编辑 | 外勤编辑 | 想去但懒、出门失败、临时局 | 流程、审批、延迟 |
| DDL 编辑 | 夜班编辑 | 期末、DDL、拖延、崩溃 | 时间幻觉、自嘲、假镇定 |

注意：这些名字不一定是最终展示名。核心是：**它们都属于同一个编辑部**。

### 5.2 为什么这比 v0.2 更好

v0.2：

```text
省电猫 / 嘴硬鹅 / 后台进程 / 勿扰牌 / 出门审批处 / DDL 小鬼
```

问题：来源割裂。

v0.3：

```text
省电编辑 / 嘴硬编辑 / 后台编辑 / 边界编辑 / 出门编辑 / DDL 编辑
```

好处：

- 统一世界观；
- 每个角色功能清楚；
- 视觉可以统一；
- 后续能扩展新编辑；
- 用户能理解“我找谁改稿”；
- 产品从“模板集合”变成“内容机构”。

### 5.3 角色是否还需要具象形象？

需要。

但形象不是“随机动物”，而是：

> 编辑部成员的具象化头像/身体/工位。

可以是：

- 小动物编辑；
- 小人编辑；
- 物件拟人编辑；
- 怪物编辑；
- 混合体。

但它们必须遵守同一套设计系统：

- 都在编辑部；
- 都有工位/栏目/岗位；
- 都拿着稿件/便签/红笔/键盘/印章；
- 都使用统一视觉语言。

这样既保留具象依赖，又不割裂。

## 6. 栏目系统

编辑部不只有人，还要有栏目。

栏目是复用和扩展的基础。

### 6.1 P0 栏目

| 栏目 | 负责内容 | 对应编辑 |
|---|---|---|
| 今日不营业 | 低电量、拒绝社交 | 省电编辑 |
| 本人暂不认领 | 嘴硬、被说中 | 嘴硬编辑 |
| 后台正在开会 | 脑补、复盘、内心戏 | 后台编辑 |
| 今日不对外开放 | 边界、勿扰 | 边界编辑 |
| 出门申请处理中 | 想出门又不想 | 出门编辑 |
| 理论上还来得及 | DDL、拖延、期末 | DDL 编辑 |

用户可以记住的是栏目，不只是角色。

例如：

- “我今天投了《今日不营业》”；
- “你适合《本人暂不认领》”；
- “我们宿舍都是《后台正在开会》”。

这能形成更强的传播语言。

### 6.2 栏目和角色关系

P0 先一人一栏目，降低复杂度。

P1 可以扩展：

- 同一栏目不同编辑改稿；
- 同一编辑跨栏目；
- 热门栏目加更；
- 用户投稿进入栏目。

## 7. 用户链路 v0.3

### 7.1 主流程

```text
入口：今天的状态交给编辑部
  ↓
选择栏目 / 编辑
  ↓
选择今天的稿件方向（状态）
  ↓
编辑部出 3 版稿
  ↓
用户选一版保存/发出去
  ↓
朋友评论/补稿/认领
  ↓
用户回流：给朋友投稿 / 换栏目 / 今日再投一篇
```

### 7.2 用词替换

| v0.2 用词 | v0.3 用词 |
|---|---|
| 选角色 | 选编辑 / 选栏目 |
| 选状态 | 投递今日状态 / 选择稿件方向 |
| 生成卡 | 编辑部出稿 |
| 换一句 | 换一版稿 |
| 给朋友生成 | 给朋友投稿 |
| 卡册 | 我的投稿箱 / 已发表 |
| 分享图 | 今日稿件 / 状态稿 |

这套语言更统一，也更容易扩展。

### 7.3 Friction 控制

不能把流程变成复杂投稿系统。

P0 仍保持 2.5 步：

1. 选栏目/编辑；
2. 选状态方向；
3. 选择用途（可跳过）。

前端展示可以是轻的：

```text
今天投哪个栏目？
[今日不营业] [本人暂不认领] [后台正在开会] ...

这篇稿子大概是什么状态？
[低电量] [想去但懒] [被说中了] ...
```

## 8. 输出结构 v0.3

输出卡不是“状态卡”，而是“编辑部出稿”。

### 8.1 卡片结构

```text
《今日不营业》
省电编辑 · 已改稿

人在。
电不在。

状态：低电量社交中

读者请勿催更。
```

### 8.2 关键元素

| 元素 | 作用 |
|---|---|
| 栏目名 | 形成传播记忆 |
| 编辑名 | 形成角色依赖 |
| 正文 | 替用户发声 |
| 状态标签 | 给朋友认领/评论的锚点 |
| 留白钩子 | 让朋友接话 |

### 8.3 示例

#### 今日不营业 / 省电编辑

```text
《今日不营业》
省电编辑 · 已改稿

人在。
电不在。

状态：低电量社交中

读者请勿催更。
```

#### 本人暂不认领 / 嘴硬编辑

```text
《本人暂不认领》
嘴硬编辑 · 已改稿

我没有被说中。
只是这篇稿子比较会碰瓷。

状态：暂不承认

评论区不要乱认领。
```

#### 后台正在开会 / 后台编辑

```text
《后台正在开会》
后台编辑 · 已改稿

表面：哈哈。
后台：复盘、脑补、模拟三种结局。

状态：高负载运行中

请勿强制关机。
```

#### 出门申请处理中 / 出门编辑

```text
《出门申请处理中》
出门编辑 · 已改稿

你的出门申请已提交。
目前卡在：床的意见。

状态：流程未走完

请勿催办。
```

### 8.4 分享后发生什么

朋友评论不是被产品写死的，而是自然发生：

```text
这不就是你。
嘴硬编辑常驻了。
你这篇应该发《今日不营业》。
给我也投一篇。
```

## 9. 视觉系统 v0.3

### 9.1 统一母视觉：编辑部

所有视觉必须来自同一个世界。

关键词：

- 编辑部工位；
- 稿纸；
- 红笔；
- 便签；
- 栏目牌；
- 已改稿章；
- 投稿箱；
- 错别字圈画；
- 低保真但有手工感；
- 像学生自己做的小刊物，不像商业海报。

### 9.2 角色视觉

每个编辑可以具象化，但必须有统一职场/编辑部语境。

| 编辑 | 视觉识别 |
|---|---|
| 省电编辑 | 趴在工位、台灯快灭、电量格贴纸 |
| 嘴硬编辑 | 红笔很多、每句都划掉又重写、仰头不认 |
| 后台编辑 | 桌上开很多窗口/稿纸/脑内便利贴 |
| 边界编辑 | 工位有小围栏、勿扰牌、校对尺 |
| 出门编辑 | 外勤包、审批单、门口但没出门 |
| DDL 编辑 | 夜班工位、咖啡、倒计时、乱稿堆 |

### 9.3 视觉不能做成“六个不同 IP 拼盘”

禁止：

- 每个角色完全不同画风；
- 一个像动物，一个像系统，一个像海报，互相不属于同一产品；
- 只做可爱头像，没有编辑部关系；
- 角色没有岗位，没有栏目，没有共同场景。

必须：

- 同一世界观；
- 同一排版语言；
- 同一材料系统；
- 同一文字层级；
- 同一“编辑部出稿”逻辑。

## 10. 传播机制 v0.3

### 10.1 栏目名是传播单位

比单个角色更容易传播的是栏目。

用户会说：

- “我今天是《今日不营业》”；
- “你适合投《本人暂不认领》”；
- “我们宿舍全在《后台正在开会》”；
- “给我也改一篇”。

### 10.2 评论区接话口

卡片结尾要留下接话口：

- `读者请勿催更。`
- `评论区不要乱认领。`
- `本稿不接受本人反驳。`
- `如有雷同，请自行入座。`
- `欢迎投稿，不保证通过。`

这些句子不是 CTA，而是社交引线。

### 10.3 二次传播

朋友可以：

- 截图用户卡片评论；
- 给自己投同一栏目；
- @另一个朋友“你也该投”；
- 改备注/改群名/贴标签；
- 在评论区补一版标题。

这比“保存图片”更重要。

## 11. 复用和依赖机制 v0.3

### 11.1 每日投稿

用户每天都可以投一篇：

- 今天低电量；
- 明天嘴硬；
- 后天 DDL；
- 周末出门审批；
- 群聊冷场找后台编辑。

### 11.2 常驻编辑

用户会形成偏好：

- “我常驻省电编辑”；
- “嘴硬编辑最懂我”；
- “DDL 编辑最近天天加班”。

### 11.3 投稿箱

本地保存历史：

- 我的投稿箱；
- 常投栏目；
- 收藏稿件；
- 给朋友投过的稿。

P0 可用 localStorage，不需要登录。

### 11.4 编辑部加更

后续运营可以说：

- 《今日不营业》加更；
- DDL 编辑夜班特刊；
- 周末出门审批专刊；
- 期末后台崩溃特刊。

这给内容运营和产品更新提供统一框架。

## 12. MVP 范围 v0.3

### 12.1 P0 做什么

- 6 个编辑；
- 6 个栏目；
- 每个栏目 6-8 个状态方向；
- 每个状态方向 4-6 条稿件文案；
- 3 种用途：发群 / 朋友圈 / 微信状态；
- 出 3 版稿；
- 换一版；
- 保存图片；
- 给朋友投稿；
- 本地投稿箱；
- 基础埋点。

### 12.2 P0 不做什么

- 不做 AI 自由生成；
- 不做账号系统；
- 不做公开投稿墙；
- 不做匿名锐评；
- 不做复杂编辑器；
- 不做心理诊断；
- 不做一堆割裂角色。

### 12.3 内容规模

```text
6 栏目 × 8 状态 × 5 文案 = 240 条核心稿件
3 种用途做轻改写
```

规则模板足够验证，不需要上来做 AI。

## 14. 为什么这是更整体的产品

v0.2 是：

```text
一组能替用户说话的角色
```

v0.3 是：

```text
一个专门替用户编辑状态的机构
```

差异：

| 维度 | v0.2 | v0.3 |
|---|---|---|
| 角色来源 | 割裂 | 同属编辑部 |
| 产品记忆 | 角色散点 | 编辑部整体 |
| 复用方式 | 找角色 | 投稿/栏目/编辑 |
| 视觉语言 | 容易拼盘 | 工位/稿纸/栏目统一 |
| 运营扩展 | 加角色 | 加栏目/加特刊/加编辑 |
| 情绪依赖 | 喜欢某角色 | 常投某栏目/找某编辑 |
| 爆款语言 | 角色名传播 | 栏目名 + 编辑名共同传播 |

## 15. 下一步建议

### 15.1 先冻结世界观

先确认：是否采用“情绪编辑部 / 今日状态编辑部”作为母世界观。

如果母世界观不确认，继续打磨角色会继续割裂。

### 15.2 再做编辑部角色压力测试

不是 30 个散点角色，而是：

```text
10 个栏目候选 × 每个 2 个编辑候选 × 每个 5 条稿件
```

看哪组最有传播和依赖潜质。

### 15.3 给 Phoebe 的设计 brief 应变成

不是：

> 画 6 个角色。

而是：

> 设计一个“不太正经但很懂人的编辑部”世界观；里面有 6 个岗位/栏目/编辑，所有角色属于同一空间、同一材料、同一排版系统。

### 15.4 给 Lucy 的文案 brief 应变成

不是：

> 给 6 个角色写文案。

而是：

> 给 6 个栏目建立固定语言风格，让用户感觉每个栏目都有稳定编辑人格。

## 16. 当前 PM 判断

我同意 Jonathan 的判断：v0.2 角色选取是割裂的。

更成熟的方向不是继续发散角色，而是建立一个完整母系统。

当前最值得推进的是：

> **今日状态编辑部**：一个替用户把今日状态改成可发布内容的低压情绪表达应用。

它比“具象情绪代理人”更像一个产品，也更像一个可以长期运营和被记住的世界。
